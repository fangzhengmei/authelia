# 第二因素厂商预校验与正式签名流程分析（校准版）

## 1. 概述

本文档校准分析 Authelia 中第二因素认证（以 Duo 为例）的**预校验（PreAuth）**与**正式签名（Auth）**两次远端调用之间的状态衔接机制，重点澄清：
- 预校验返回 `allow` 会**直接触发会话升级**，不必进入正式签名
- 预校验失败、首选设备失效、无可用设备三条分支的后续走向
- 所有状态转移的触发条件与结果

## 2. 核心控制流总览

### 2.1 主控函数与关键判定点

**文件**：`internal/handlers/handler_sign_duo.go:129-146`

```go
func HandleDuoAuthentication(ctx, userSession, duoAPI, bodyJSON) error {
    // 分支A: 无首选设备
    duoDevice, err := ctx.Providers.StorageProvider.LoadPreferredDuoDevice(...)
    if err != nil {
        selectedDevice, selectedMethod, err := HandleInitialDeviceSelection(...)
        if err != nil {
            return err  // 预校验网络错误，直接返回
        }
        // 关键：只有返回非空 device/method 才会进入 AuthCall
        return PerformDuoAuthenticationIfValid(ctx, userSession, duoAPI, selectedDevice, selectedMethod, bodyJSON)
    }

    // 分支B: 有首选设备
    selectedDevice, selectedMethod, err := HandlePreferredDeviceCheck(...)
    if err != nil {
        return err  // 预校验网络错误，直接返回
    }
    // 关键：只有返回非空 device/method 才会进入 AuthCall
    return PerformDuoAuthenticationIfValid(ctx, userSession, duoAPI, selectedDevice, selectedMethod, bodyJSON)
}
```

**关键守卫**：`internal/handlers/handler_sign_duo.go:99-113`

```go
func PerformDuoAuthenticationIfValid(ctx, userSession, duoAPI, device, method, bodyJSON) error {
    // ⚠️  核心判定：只有 device 和 method 都非空时才执行 AuthCall
    if device == "" || method == "" {
        return nil  // 静默返回，不进入正式签名
    }

    // 执行正式签名
    if err := PerformDuoAuthentication(...); err != nil {
        return err
    }

    // 正式签名成功，更新会话
    HandleAllow(ctx, userSession, bodyJSON)
    return nil
}
```

## 3. 状态转移矩阵

### 3.1 预校验结果状态转移

| 预校验结果 | 触发条件 | 返回 (device, method, err) | 是否进入 AuthCall | 会话变化 | 响应动作 |
|-----------|---------|---------------------------|------------------|---------|---------|
| **网络错误（无首选分支）** | HTTP 请求失败、超时、解析错误 | `("", "", err)` | ❌ 否 | 无变化 | 写入 401 响应，已写响应后终止 |
| **网络错误（有首选分支）** | HTTP 请求失败、超时、解析错误 | `("", "", nil)` | ❌ 否 | 无变化 | 写入 401 响应，已写响应后终止 |
| **enroll** | 用户未在 Duo 注册 | `("", "", nil)` | ❌ 否 | 无变化 | 写入 enroll + 注册 URL JSON，已写响应后终止 |
| **deny（无首选分支）** | Duo 策略拒绝该用户，无首选设备 | `("", "", nil)` | ❌ 否 | 无变化 | 写入 `{"result": "deny"}` JSON，已写响应后终止 |
| **deny（有首选分支）** | Duo 策略拒绝该用户，有首选设备 | `("", "", nil)` | ❌ 否 | 无变化 | 调用 ReplyUnauthorized 返回 401，已写响应后终止 |
| **allow** | Duo 直接允许（绕过） | `("", "", nil)` | ❌ 否 | ✅ 升级为 2FA | 调用 HandleAllow 更新会话，已写响应后终止 |
| **unknown result** | Duo 返回未识别的 result 值 | `("", "", err)` | ❌ 否 | 无变化 | 错误上抛，上层按错误路径返回 401 |
| **auth + 无设备** | 用户注册了但无可用设备 | `("", "", nil)` | ❌ 否 | 无变化 | 写入 enroll JSON，已写响应后终止 |
| **auth + 多设备** | 多个设备需用户选择 | `("", "", nil)` | ❌ 否 | 无变化 | 写入设备列表 JSON，已写响应后终止 |
| **auth + 单设备** | 恰好一个设备可用 | `(device, method, nil)` | ✅ 是 | 待 AuthCall 结果 | 进入正式签名 |
| **auth + 首选有效** | 首选设备仍然有效 | `(device, method, nil)` | ✅ 是 | 待 AuthCall 结果 | 进入正式签名 |

### 3.2 正式签名（AuthCall）结果状态转移

| AuthCall 结果 | 触发条件 | 会话变化 | 响应动作 |
|--------------|---------|---------|---------|
| **网络错误** | HTTP 请求失败、超时 | 无变化 | 返回 401 认证失败 |
| **result != allow** | Duo 返回 deny 等 | 无变化 | 记录失败日志，返回认证失败 |
| **result == allow** | Duo 认证通过 | ✅ 升级为 2FA | 调用 HandleAllow 更新会话 |

### 4.1 分支一：预校验失败

**代码位置**：`internal/handlers/handler_sign_duo.go:117-123` 与 `242-248`

```go

    ctx.Logger.Errorf("Failed to perform Duo PreAuth ...")

    return "", "", err  // 返回 err
}

// HandlePreferredDeviceCheck 中（有首选设备分支）

    ctx.Logger.Errorf("Failed to perform Duo PreAuth ...")
    respondUnauthorized(ctx, messageMFAValidationFailed)  // 直接回 401
    return "", "", nil  // ⚠️  返回 nil 不返回 err，已写入响应，上层收到空值后静默终止
}
```

**状态转移**：
```
        ┌───────────────────────────────────────────────────────────────────┐
        │                       预校验失败分岔路                            │
        └───────────────────────────────┬───────────────────────────────────┘
                                        │
                ┌───────────────────────┴───────────────────────┐
                │                                               │
                ▼                                               ▼
    无首选设备分支（HandleInitialDeviceSelection）    有首选设备分支（HandlePreferredDeviceCheck）
                │                                               │
                ▼                                               ▼
      respondUnauthorized(401)                        respondUnauthorized(401)
                │                                               │
                ▼                                               ▼
      return ("", "", err)                             return ("", "", nil)
                │                                               │
                ▼                                               ▼
  HandleDuoAuthentication 收到 err             HandleDuoAuthentication 收到 ("", "", nil)
                │                                               │
                ▼                                               ▼
      DuoPOST 收到 err ──► respondUnauthorized(401)    PerformDuoAuthenticationIfValid
                                                          device/method 为空，return nil
                │                                               │
                ▼                                               ▼
        已写响应后终止                                   已写响应后终止
```

**结论**：预校验失败 **直接写入 401 响应**，**不会**进入 AuthCall。区别在于：
- 无首选设备分支：返回 `err`，上层再次回响应（幂等）
- 有首选设备分支：返回 `nil`，上层通过空 device/method 静默终止

## 5. 会话推进机制（校准版）

### 5.1 会话升级的两个触发点

会话从 1FA 升级到 2FA 有且仅有两个路径：

| 触发点 | 位置 | 条件 |
|-------|------|------|
| **路径A** | `HandleDuoPreAuthResult:169-173` | 预校验直接返回 `allow` |
| **路径B** | `PerformDuoAuthenticationIfValid:110` | 正式签名返回 `allow` |

两条路径最终都调用同一个函数：

**文件**：`internal/handlers/handler_sign_duo.go:324-352`

```go
func HandleAllow(ctx *middlewares.AutheliaCtx, userSession *session.UserSession, bodyJSON *bodySignDuoRequest) {
    // 1. 重新生成会话ID（安全最佳实践）
    if err = ctx.RegenerateSession(); err != nil {
        respondUnauthorized(ctx, messageMFAValidationFailed)
        return
    }
    
    // 2. 更新会话认证状态为 2FA
    userSession.SetTwoFactorDuo(ctx.GetClock().Now())
    
    // 3. 持久化会话
    if err = ctx.SaveSession(*userSession); err != nil {
        respondUnauthorized(ctx, messageMFAValidationFailed)
        return
    }
    
    // 4. 返回响应（重定向或 OIDC 流程）
    if len(bodyJSON.Flow) > 0 {
        handleFlowResponse(...)
    } else {
        Handle2FAResponse(ctx, bodyJSON.TargetURL)
    }
}
```

## 7. 设计要点总结

### 7.1 核心设计原则

1. **空值守卫**：通过 `PerformDuoAuthenticationIfValid` 中的 `device == "" || method == ""` 判断，统一控制是否进入正式签名
2. **提前终止**：所有不需要正式签名的场景（enroll/deny/allow/多设备选择）都通过返回空 device/method 提前终止
3. **单一会话入口**：只有 `HandleAllow` 能升级会话，保证会话状态变更的原子性
4. **防御性清理**：首选设备失效时主动清理持久化存储，避免脏数据影响后续流程

### 7.2 提前返回分支调用集合

所有提前返回（不进入 AuthCall）的分支分为两类：

**A. 直接写入响应型**：在当前函数内完成响应写入
- `ctx.SetJSONBody(...)`：写入结构化 JSON 响应（enroll/deny/设备列表等）
- `ctx.ReplyUnauthorized()`：直接返回 401 未授权（有首选分支的 deny 场景）
- `respondUnauthorized(ctx, ...)`：封装的 401 响应（网络错误场景）
- `HandleAllow(...)`：会话升级后的响应（allow 场景）

**B. 错误上抛型**：不写响应，由上层统一处理
- `return "", "", fmt.Errorf("unknown result: %s", result)`：未知 result 时错误上抛，上层按错误路径返回 401

### 7.3 关键校准点回顾

| 之前结论（需校准） | 校准后结论 | 依据 |
|------------------|-----------|------|
| 预校验 allow 是"特殊情况" | 预校验 allow 是**一等公民**，与正式签名成功平级，直接调用 HandleAllow | `HandleDuoPreAuthResult:171` 与 `HandlePreferredDeviceCheck:270` |
| 首选设备失效后回退到手动选择 | 首选设备失效后**可能自动选择新设备继续 AuthCall**，也可能回退 | `HandleAuthResult:226` → `HandleAutoSelection:313-321` |
| 失败分支会话影响描述模糊 | 预校验阶段**所有失败都不修改会话**，只有 HandleAllow 能升级会话 | 代码中只有 HandleAllow 调用 `SetTwoFactorDuo` |
| 预校验失败统一返回 err | 无首选分支返回 `err`，有首选分支写入 401 后返回 `nil`，上层静默终止 | `HandleInitialDeviceSelection:121` vs `HandlePreferredDeviceCheck:247` |
| 分支终止表述为"无响应" | 所有终止分支都**已写入响应**或**错误上抛由上层写响应**，表述为"已写响应后终止" | 直接写响应的分支调用 SetJSONBody/ReplyUnauthorized/respondUnauthorized，错误上抛分支由上层处理 |
| deny 两条路径响应相同 | 无首选分支返回 `{"result": "deny"}` JSON，有首选分支调用 ReplyUnauthorized 返回 401 | `HandleDuoPreAuthResult:163` vs `HandlePreferredDeviceCheck:265` |
| "其他"分支直接写响应返回空值 | "其他"分支（default）走错误上抛路径，返回 `("", "", err)`，由上层按错误路径返回 401 | `HandleDuoPreAuthResult:179` 与 `HandlePreferredDeviceCheck:277` |

### 7.4 协议层切面

**文件**：`internal/duo/types.go:14-24`

```go
// BaseProvider 描述上游厂商的签名调用能力（仅 HTTP 签名）
type BaseProvider interface {
    SignedCall(method string, uri string, params url.Values, options ...duoapi.DuoApiOption) (*http.Response, []byte, error)
}

// Provider 描述业务层使用的能力（PreAuth / Auth 语义）
type Provider interface {
    Call(ctx middlewares.Context, userSession *session.UserSession, values url.Values, method string, path string) (*Response, error)
    PreAuthCall(ctx middlewares.Context, userSession *session.UserSession, values url.Values) (*PreAuthResponse, error)
    AuthCall(ctx middlewares.Context, userSession *session.UserSession, values url.Values) (*AuthResponse, error)
}
```

协议层切面的作用：
- 下层 `SignedCall`：对 `duo_api_golang` 库的薄封装，仅负责签名 HTTP 调用
- 中层 `Call`：统一处理响应解析、状态码转换、错误包装
- 上层 `PreAuthCall` / `AuthCall`：业务语义接口，供 handler 层调用
- 两层接口设计实现了关注点分离，便于测试和扩展
